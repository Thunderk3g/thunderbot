## (a) Summary of the most important confirmations and corrections

**Corrections that change the report's argument**

1. **Vercel Hobby can now schedule every 15 minutes, in IST, through Vercel Schedules (public beta).** The report says "Hobby cannot wake the worker every few minutes" and "Vercel Hobby's own cron is useless for this job", and that Schedules' "Hobby frequency limits could not be confirmed". The live limits page gives Hobby a "Most frequent cron schedule" of "Every 15 minutes" with a jitter window that is "Always 15 minutes", an IANA `timezone` per schedule, and a `path` target that sends `Authorization: Bearer <CRON_SECRET>` exactly like a cron job. A Hobby schedule `10 15 * * 1-5` with `"timezone": "Asia/Kolkata"` would therefore start between 15:10 and 15:25 IST (inference from the jitter rule). It is beta, has no retries for path or function targets, and Hobby is capped at 5,000 schedule runs per billing period. Supabase pg_cron remains the more punctual free option (to-the-minute), but it is no longer the only free one inside the two vendors.
2. **A once-a-day cron expression deploys on Hobby; it is the timing, not the deployment, that fails the 15:10 requirement.** The report's note that "the `crons` block needs Pro" is too strong. Only expressions that "would run more than once per day" fail deployment. On Hobby the run fires "at any point within the specified hour", so `40 9 * * 1-5` fires somewhere in 09:00:00–09:59:59 UTC (14:30–15:29 IST) by the docs' own wording, although the docs' examples all use minute 0.
3. **Vercel's documented way to put Python beside Next.js is now "Services" (beta, all plans), not the `api/` directory.** The Python page says "To run a Python backend and a frontend together in one project, you can use Services", and describes `api/*.py` as support for "existing projects". Services use an explicit, ordered rewrite table in a root `vercel.json`, which also answers two things the report left open: path precedence (first matching rewrite wins, routing is final) and how a `worker/` folder that is a sibling of `dashboard/` reaches the build (each service has its own `root`, "relative to `vercel.json`"). The older `experimentalServices` key is rejected for projects created on or after 6 July 2026.
4. **GitHub no longer states included Actions usage in minutes.** GitHub Free now includes "$12 USD" of compute usage a month; at the documented $0.006 per minute for a standard Linux runner that equals 2,000 minutes (my arithmetic), so the report's "44 of 2,000 minutes" is still right in substance but the unit has changed.
5. **Cloud NAT is far cheaper than "about $32 a month" for one small workload, on the page's own formula.** The gateway costs "$0.0014 * the number of VM instances that are using the gateway" per hour up to 32 instances; $0.044 an hour (about $31.68 for 720 hours) is the cap above 32 instances. One instance plus one external IP works out at about $4.61 a month plus $0.045 per GiB (my arithmetic). How Cloud Run instances are counted, and any VPC connector cost, were not on a reachable page.

**Confirmations (the report was right)**

- Vercel cron table: 100 cron jobs per project on every plan; Hobby "Once per day", "Per-hour (±59 min)"; Pro "Once per minute", "Per-minute". UTC only; no `MON`/`JAN` names; production only; HTTP GET with user agent `vercel-cron/1.0`.
- `CRON_SECRET` is sent as `Authorization: Bearer <secret>`; failed crons are not retried; a run can be delivered twice or missed; overlapping runs are possible. All four were [recalled] in the report and are now confirmed word for word.
- Cron Jobs are labelled a legacy feature to be migrated to Schedules; Schedules is in beta.
- Function duration: Hobby 300 s default and maximum; Pro 300 s default, 800 s maximum (plus a new 1,800 s beta). Memory: Hobby 2 GB / 1 vCPU; Pro up to 4 GB / 2 vCPU. Fluid compute default for new projects since 23 April 2025. Python bundle limit 500 MB. Request and response body 4.5 MB.
- Hobby is single-region and **can** choose it: "Hobby plans can select any single region", and `bom1` (Mumbai) is in the region list.
- Vercel Pro: "$20/month Pro platform fee" including "$20/month in usage credit". Hobby: "restricted to non-commercial personal use only".
- Static IPs: Pro and Enterprise only, "$100/month per project, plus Private Data Transfer", shared: "a small group of customers in the same region shares them". Dedicated addresses only through Secure Compute, Enterprise only, custom pricing.
- Python on Vercel is generally available (changelog dated 15 October 2026); versions 3.12 (default), 3.13, 3.14.
- Supabase: every SQL block quoted in the report matches the live docs. Free projects "are paused after 1 week of inactivity"; restore window "up to 1 year"; pg_net default timeout 2,000 ms; Edge Functions 256 MB, 150 s (Free) / 400 s (paid), 2 s CPU; Pro "From $25 / month"; outbound IP "not static".
- GitHub: `schedule` now accepts a `timezone` field; shortest interval 5 minutes; delay and dropped-run wording; 60-day disabling applies "In a public repository"; static IPs only on larger runners (Team or Enterprise Cloud).
- Google: Cloud Run free tier applies to jobs; Mumbai (asia-south1) is Tier 1; Cloud Scheduler gives "3 jobs per month free" per billing account.

**Still unconfirmed after this pass**

- Any official sentence that Next.js middleware runs in front of non-Next `api/*.py` functions; path precedence between `api/*.py` and `app/api/**/route.ts` in a plain (non-Services) project.
- Function duration limits *without* Fluid compute (60 s / 300 s): the current docs no longer publish them.
- The 225 MB Python bundle threshold (from builder source code); the docs mention only 500 MB and a 5 GB large-functions beta.
- An explicit "available on Free" statement for Supabase Cron, pg_net or Vault; whether pg_cron activity prevents pausing.
- Whether Vercel Static IPs are offered in `bom1` (no list of supported regions is published; only a `bom1` Private Data Transfer price).
- Cloud Scheduler's timezone support and the Google free-tier documentation page: `docs.cloud.google.com` is blocked by the proxy.

## (c) New facts worth adding

**Vercel Schedules (public beta, announced 4 November 2026)**

- Three targets: "**Function** — Vercel invokes a private Vercel Function that has no public URL"; "**Path** — Vercel sends an HTTP request to a path on your deployment, like a Cron Job"; "**Queue topic**". Static schedules live in `vercel.json` under `schedules`; dynamic ones are created with `@vercel/schedules` or the `vercel schedules` CLI and can only target a queue topic. — https://vercel.com/docs/schedules (2026-10-26)
- Configuration syntax, from the official reference: `"schedules": {"daily-report": {"schedule": "0 9 * * *", "path": "/api/daily-report", "requestMethod": "GET"}}`, with optional `"timezone": "America/New_York"` and `"jitter": 5`. "`requestMethod` — HTTP method for `path`. Defaults to `POST`." "`jitter` — Jitter window in minutes, from 1 to 15. Defaults to 1 on Pro and Enterprise. Hobby always uses 15." — https://vercel.com/docs/schedules/configuration
- Path targets authenticate exactly like cron jobs: "The `user-agent` header is `vercel-cron/1.0`"; "If you set `CRON_SECRET`, the `Authorization` header contains `Bearer <CRON_SECRET>`". They also carry an execution ID in the `ce-id` header, which "Stays the same if the run is delivered more than once" and is the documented idempotency key. — https://vercel.com/docs/schedules/migrate-from-cron-jobs (2026-10-09); https://vercel.com/docs/schedules/handle-runs
- No retries for path or function targets: "Path — No. Vercel doesn't retry a run if your route returns an error or times out." "If a failed run must be retried, target a queue topic." — https://vercel.com/docs/schedules/concepts
- Late runs are delivered late and then expire: "An occurrence expires after its jitter window plus the shortest interval between the schedule's runs." "For `0 9 * * 1-5` (weekdays at 09:00), the shortest interval is one day. Friday's occurrence expires on Saturday at 09:01". After an outage, "Vercel delivers every occurrence that hasn't expired", so a frequent schedule "can run several times in quick succession". The handler should "compare the scheduled time to the current time and return early" if the run is stale. — same
- Timezones follow daylight saving; India has none, so `Asia/Kolkata` is stable. — same
- Hobby over-limit behaviour: when a Hobby team exceeds 5,000 runs or 500 dynamic schedules in a billing period, "Scheduled runs, which Vercel skips" until the next period. On downgrade to Hobby, Vercel **deletes** schedules that can run more often than every 15 minutes. — https://vercel.com/docs/schedules/limits
- Schedules, unlike cron jobs, also run in Preview and custom environments, but "New static schedules in Preview and custom environments start inactive by default". — https://vercel.com/docs/schedules/quickstart
- Inference for Thunderbot: a five-minute tick is not possible on Hobby through Schedules, a 15-minute tick is. `*/15 3-10 * * 1-5` would be 32 runs a trading day, roughly 700 a month, inside the 5,000-run Hobby cap (my arithmetic).

**Vercel Cron Jobs**

- Every cron request carries "an `x-vercel-cron-schedule` header containing the cron expression that triggered the invocation", and the same path may appear in several `crons` entries with different schedules (the docs' own example lists `/api/sync` twice). This closes the notes' gap on shared paths. — https://vercel.com/docs/schedules/cron-jobs/manage-cron-jobs (2026-08-11)
- The secret is frozen per deployment: "A deployment captures `CRON_SECRET` from your project settings when it builds, and keeps that copy for its lifetime." "Editing `CRON_SECRET` in project settings changes nothing until your next deployment." This matters if the same secret is also stored in Supabase Vault: rotate both, then redeploy. — same
- Header-safe characters only: "Don't include line breaks or leading or trailing spaces … If the header doesn't match the value your code reads, your endpoint returns `401` for every invocation." — same
- Redirects are fatal and silent: "Cron jobs do not follow redirects." With Next.js `trailingSlash` on, "a request to `/api/cron` redirects to `/api/cron/`, so the cron job never reaches your function." "when cron jobs respond with a redirect or a cached response, they will not be shown in the logs." — same
- A firewall rule can block the scheduler: "A WAF custom rule matches the cron request … exclude the cron job's path from rules that deny or challenge traffic." — same
- A cron pointing at a missing path "generates a 404 error. However, **Vercel still executes your cron job**." "There is currently no support for `vercel dev`, `next dev`" for cron jobs. — same
- During a promotion or rollback, "A run scheduled inside that gap can still reach the deployment you just moved away from, or it can be skipped." — same

**Vercel Python and Services**

- Python framework apps (FastAPI, Flask, Django) build "into a single Vercel Function from its resolved entrypoint"; entrypoint files searched are "`app.py`, `index.py`, `server.py`, `main.py`, `wsgi.py`, or `asgi.py`", the same names inside `src/` or `app/`, or `tool.vercel.entrypoint` in `pyproject.toml`. Key `functions` on that entrypoint file, for example `"app/main.py": {"maxDuration": 60}`. — https://vercel.com/docs/functions/runtimes/python (2026-08-12); https://vercel.com/docs/functions/configuring-functions/duration
- Hazard for the `api/` layout: if a Python framework preset is detected, "files under `/api` don't become separate Vercel Functions". — https://vercel.com/docs/functions/runtimes/python/api-directory
- "By default, Python Vercel Functions include all files from your project that are reachable at build time. There is no automatic tree-shaking for Python." "The working directory is the base of your project, not the directory containing the file." Streaming responses are supported. — https://vercel.com/docs/functions/runtimes/python
- Services billing and limits: "Each service runs on Vercel's compute and is billed the same as Vercel Functions"; "The same function limits apply to each service, such as memory and maximum duration." Hobby includes the "First 1,000,000" service-to-service requests. — https://vercel.com/docs/services/pricing (2026-08-31)
- Services share one front door: "Firewall, Deployment Protection, redirects are configured once at the top level and apply across all services". A schedule can target a function inside a service with `"service": "worker", "function": "index"`, though "`vercel dev` doesn't run schedules that target a function in a service yet." — https://vercel.com/docs/services; https://vercel.com/docs/schedules/configuration
- Vercel's own advice against over-using Services: "For an app that one framework already handles, such as Next.js with API routes, deploy the project as usual." — https://vercel.com/kb/guide/vercel-services (2026-10-22)
- Routing Middleware can now be written in Python (`"proxy": {"entrypoint": "proxy:proxy"}`), but "Your Routing Middleware must use the same runtime as your app" and `proxy` cannot be combined with Next.js. — https://vercel.com/docs/routing-middleware (2026-08-14)

**Supabase**

- Pause warning: "A warning email roughly one week before the pause takes effect", then "A confirmation email once the project has been paused." — https://supabase.com/docs/guides/platform/free-project-pausing
- Free plan quotas on the pricing page: "Unlimited API requests", "50,000 monthly active users", "500 MB database size", "Shared CPU • 500 MB RAM", "5 GB egress", "5 GB cached egress", "1 GB file storage", "Limit of 2 active projects"; log retention "1 day". — https://supabase.com/pricing
- Cron job names: "Job names are case sensitive and cannot be edited once created. Attempting to create a second Job with the same name (and case) will overwrite the first Job." Sub-minute schedules ("`30 seconds`") need "Postgres version 15.1.1.61 or later". Jobs can be paused with `cron.alter_job(job_id := …, active := false)`. — https://supabase.com/docs/guides/cron/quickstart
- Edge Functions also have a "Request idle timeout: 150s" and a size limit of "20MB (bundled locally via the CLI)". — https://supabase.com/docs/guides/functions/limits

**GitHub Actions**

- With a `timezone`, daylight-saving gaps are handled ("a 2:30 AM schedule advances to 3:00 AM"); irrelevant for `Asia/Kolkata`. Weekday and month names (`SUN-SAT`, `JAN-DEC`) are accepted, unlike Vercel. — https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows
- "Scheduled workflows will only run on the default branch." A commit that changes the cron line re-activates a disabled scheduled workflow. — same

**Google Cloud**

- The Cloud Run free tier is per billing account, not per project, and is applied as a discount at Tier 1 (us-central1) prices; Mumbai is itself Tier 1, so the allowance stretches as far there as in Iowa. — https://cloud.google.com/run/pricing
- Outbound data from Cloud Run "uses the Premium Network Service Tier" with "1GiB free data transfer within North America per month", so traffic out of Mumbai is not covered by that allowance. — same
